## 1. 项目简介

**一句话**：给一个中心点，用百度地图公开 API 推导出「步行 15 分钟真实可达范围」，量化圈内民生设施供给，并指出供给不足的「灰色区域」。

**问题定义**（拆成三个可独立验证的子问题）：

| # | 子问题 | 交付形态 |
| --- | --- | --- |
| P1 可达性 | 从中心点出发，步行 T 分钟能到哪些地方？ | 等时圈多边形 |
| P2 覆盖性 | 等时圈里有多少各类设施？最近的要多久？ | 六维覆盖统计 + 评分 |
| P3 公平性 | 圈内哪些位置三类基础配套都够不着？ | 盲区清单 + 灰色区域 |

**核心约束**：命题要求「不获取底层路网数据」，因此本项目采用**外部测时 + 内部插值**——只通过百度批量算路 API 在若干方位上实测耗时，再用 IDW 插值推出整片连通区域的耗时场（见 §6）。

### 1.1 产品定位边界（重要）

> 🔴 CircleDoc 输出的是**辅助性量化参考**，**不是规划审批结论**。

所有结果都带数据来源标记（`live` 实时路网 / `cache` 缓存 / `sample` 程序合成）与置信度提示。评分模型的权重与阈值是**本产品的假设**，不是国家标准（见 §7）。缓存只是减少重复调用的技术措施，不是数据资产库（见 §9）。

### 1.2 功能覆盖面

| 能力 | 对应需求 |
| --- | --- |

### 2.2 零配置断言（PRD §6.2）

> 🔴 **全新 clone、不创建 `.env`、`docker compose up` → 服务照常起，能跑完一次完整体检。**

具体表现：`/api/health` 的启动探测发现没有 AK → `data_mode` 的默认值由 `live` 改为 **`mock`** → 响应里 `data_source = sample` → 首屏挂「当前为离线报告模式」横幅 → 报告（评分卡、雷达图、柱状图、明细表、盲区清单）**全部可用**，只有地图区域降级为合成 SVG 示意图。

## 3. AK 申请与两种 AK 的区别

### 3.1 两种 AK 必须分开申请，绝不能互换

| | 服务端 AK | 浏览器端 AK |
| --- | --- | --- |
| 环境变量 | `BAIDU_SERVER_AK` | `BAIDU_BROWSER_AK` |
| 谁在用 | 后端调 Web 服务 API | 前端加载 JSAPI 4.0 |
| 鉴权方式 | **IP 白名单**（支持 `0.0.0.0/0` 不限制）或 SN 校验 | **Referer 域名白名单** |

依据 **FAQ 2639**：JS API 只支持「浏览器类型」AK，Web 服务需要「服务端类型」AK。混用的表现是 **`status = 203 APP 类型错误`**——这是本项目最高频的坑（风险 R7）。

浏览器端 AK 的 Referer 白名单校验失败还会报「APP Referer 校验失败」（FAQ 2787），成因有三类：AK 类型不对 / 域名不在白名单 / 第三方组件内置他人 AK。

### 3.2 🔴 同账号下各 AK 配额共用，双 AK 不能扩配额

**FAQ 2594：同一账号下 AK 之间的配额是共用的。**

这条推翻了一个很自然的假设——「申请两个 AK 就有两份额度」。实际是：双 AK 只能**分离鉴权类型**，**一分钱额度都多不出来**，反而会因为两个 AK 抢同一个配额池而互相挤占。本项目的 API 客户端因此**删掉了按 AK 分缓存键的设计**（`ak_profile_tag` 分量），因为它只会让同一份数据缓存两遍、命中率减半，没有任何隔离收益。

### 3.3 本地开发的 Referer 白名单应填 `*`

官方对本地场景的**正面原文指引是填 `*`**：

- FAQ 2781：「**本地可以设置 `*`**，前端代码容易泄露 AK，被其他网站非法调用，上线前可以用作 Debug，线上正式 ak 请设置合理的 Referer 白名单」
- JSAPI 4.0 开发前准备：「**Referer 白名单：开发阶段填写 `*`**（上线后请改为实际域名）」

> ⚠️ **未验证**：`localhost` / `127.0.0.1` **能否**作为 Referer 白名单项被接受，**官方文档从未明文列出**。本项目只按官方正面指引写 `*`，不声称 `localhost` 可用。域名白名单的写法支持 `*.mysite.com` / `*myapp.com` / `myapp.com`，多个用英文半角逗号隔开（FAQ 2590）。

### 3.4 申请步骤

1. **完成开发者认证**（`https://lbs.baidu.com/apiconsole/auth`）。**FAQ 2614：认证不通过无法使用百度地图开放平台产品**——这一步不是可选项，`live` 模式完全依赖它。
2. 创建 **服务端类型 AK**，在【启用服务】里勾选本项目用到的服务：地理编码、逆地理编码、地点检索、地点输入提示、步行/骑行路线规划、批量算路（RouteMatrix）。少勾一项会报 **`status = 240` 服务被禁用**。
3. 创建 **浏览器类型 AK**，Referer 白名单按 §3.3 填 `*`（仅限开发阶段）。
4. 分别填入 `.env` 的 `BAIDU_SERVER_AK` / `BAIDU_BROWSER_AK`。

> ⚠️ 认证与申请时填写的**使用场景须与实际实现一致**（条款 3.2.3(iii)：场景严重不符可被封号）。建议填写「15 分钟生活圈可达性辅助分析工具（非商业、演示用途）」。

## 4. `.env` 变量表

**唯一出处是 `infra/config.py`**，`.env.example` 是它的模板（本表与之逐条对照）。**不填 `.env` 也能起服务**，此时全部取下列默认值。

变量名大小写不敏感。以下共 **55 个变量**，另有一个注释掉的可选项 `CIRCLEDOC_ENV_FILE`（指定 `.env` 之外的配置文件路径，Docker 里 cwd 与本机不同时用得上）。

### 4.1 百度 AK 与取数模式

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `BAIDU_SERVER_AK` | *（空）* | 服务端类型 AK。**留空 = 不发任何实时请求**，直接走缓存 / 合成数据 |
| `BAIDU_BROWSER_AK` | *（空）* | 浏览器类型 AK，只给前端加载 JSAPI 用，后端永不用它调 Web 服务 |
| `DATA_MODE` | `auto` | 取数策略，值域 `auto\|live\|cache\|mock`。`auto` 由 `/api/health` 启动探测解析；探测失败即改 `mock`，**不硬编码成 `live`** |

> ⚠️ 别把 `data_mode` 与 `data_source` 混为一谈：前者是**用户选的策略**（`auto/live/cache/mock`），后者是**实际取了哪一层**（`live/cache/sample`）。把 `sample` 当模式值写进前端状态机是 PRD §4.6 明确点名的错误。

### 4.4 令牌桶（按服务分桶）

不同服务稀缺度相差 50 倍（地点检索 100/日 vs 路线规划 5,000/日），共用一个桶会让稀缺的检索被廉价的路线规划挤占。

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `RATE_PLACE_QPS` / `BURST_PLACE` | `0.5` / `1` | 地点检索（**与地址联想共用**同一份 100 次/日 配额，故共用桶） |
| `RATE_REGEO_QPS` / `BURST_REGEO` | `0.5` / `1` | 逆地理编码 |
| `RATE_ROUTE_QPS` / `BURST_ROUTE` | `2.5` / `2` | 批量算路 / 路线规划 |
| `RATE_GEOCODE_QPS` / `BURST_GEOCODE` | `1.0` / `2` | 地理编码 |

> 🔴 `rate` 一律**低于**官方 3 QPS 留余量；`burst` 必须 **≤ `rate`**——桶满时一次放行多个并发必然触发 `status=401`。
> ⚠️ 上表是 PRD §4.6 的**建议值**，请以**你账号控制台的实际档位为准**（笔记 §9.2-①）。

### 4.5 单次分析的出网预算（三栏分开）

三栏混成一个数字会掩盖真实消耗：**1 次批量算路 = 1 个 HTTP 请求 = 12 个配额单位**。

| 变量 | 默认值 | 口径 |
| --- | --- | --- |
| `MAX_PLACE_CALLS_PER_ANALYSIS` | `8` | 地点检索出网次数（6 维度 + 1 便民参考 + 1 冗余） |
| `MAX_ROUTE_LINES_PER_ANALYSIS` | `150` | 路线条数，**单模式口径**；双模式按模式数折算（`Settings.route_lines_budget()`） |
| `MAX_QUOTA_UNITS_PER_ANALYSIS` | `120` | 单模式配额单位上限 |
| `MAX_QUOTA_UNITS_DUAL_MODE` | `220` | 双模式（步行 + 骑行同跑）放宽值，PRD §6.1 验收口径 |
| `MAX_HTTP_REQUESTS_PER_ANALYSIS` | `20` | 真实往返次数上限 |

> 测试提示：把 `MAX_ROUTE_LINES_PER_ANALYSIS` 临时改成 **1** 可验证「预算守护中途截停」；改成 **5000** 则永不触发。**两个方向都不该崩**（PRD §6.2 的保守默认值双向安全断言）。

### 4.6 重试与双熔断

判据一律来自 **HTTP 200 响应体里的 `status`**，不按 HTTP 状态码（详见 §6.4）。

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `RETRY_MAX_ATTEMPTS` | `3` | 最大尝试次数 |
| `RETRY_BASE_DELAY_S` | `0.5` | 指数退避基数（`0.5 s → 1 s → 2 s`） |
| `RETRY_MAX_DELAY_S` | `8.0` | 退避上限 |
| `RETRY_CONCURRENCY_FIRST_DELAY_S` | `1.0` | `status=401` 首次退避下限——QPS 窗口以秒计，退避小于 1 s 等于白重试 |
| `CONCURRENCY_BREAKER_THRESHOLD` | `5` | `concurrency_breaker`：连续 5 次失败即打开 |
| `CONCURRENCY_BREAKER_HOLD_S` | `30` | 打开时长（针对 `401`、`1`、网络超时） |
| `QUOTA_BREAKER_TZ_OFFSET_HOURS` | `8` | `quota_breaker` 命中 `4`/`302` 后打开到**次日零时**。东八区无夏令时，用固定偏移而非 `tzdata`（Windows 常缺时区库） |

### 5.1 几个容易踩的接口口径

- **`/api/regeo` 的坐标系参数名是 `coordtype`**（无下划线、传字符串），而请求里的 `location` 是 **`纬度,经度`**，本接口的入参 `lnglat` 却是 **`经度,纬度`**。换算只在 `services/geo.py` 做一次（详见 §6.4）。

## 6. 算法摘要

### 6.1 不取路网，如何推出连通区域

命题明确「不获取底层路网数据」，所以本项目**不下载也不重建路网**，而是把百度批量算路当做一个**黑盒测时器**，只在有限个方向上问它「从这里走到那里要多久」，再用这些样本**插值**出整片区域的耗时场：

```
输入：中心点 C，目标时长 T，出行方式 mode
输出：有序多边形顶点环 + 网格耗时场

Step1 粗扫    12 个方位角（间隔 30°），沿直线取探测点
              → 1 次批量算路：origins=[C]，destinations=12 个探测点 → 12 条路线，1 个 HTTP 往返
Step2 二分    在 [d_lo, d_hi] 上二分求 t(P) ≈ T 的点（容差 ±30 s，最多 5 轮）
              每轮把各方向的中点打包成 1 次批量请求
              ⚠️ 单次批量受 origins×destinations ≤ 50 约束，超过则切分
              该方向在 R_max 处耗时仍 < T → 边界外推一次，标记 extrapolated
Step3 加密    相邻顶点耗时差 > 60 s 的方向对，在中间补 15° 方向（自适应，总顶点 12~36）
Step4 排序   按方位角升序排列（消除自交）→ Douglas-Peucker 简化（容差 15 m）
              ⚠️ 阻隔顶点受保护、不参与简化
Step5 补路径 批量算路**不返回 polyline**；只有用户点击某个顶点时才为该方向补调 direction
Step6 耗时场 对圈内 250 m 网格点做 IDW 插值（反距离加权，p=2，取最近 8 个实测点）
```

**为什么这样能推出连通区域**：道路非直线，所以同一方位上「耗时 = T」的那个距离就是该方向的真实可达边界；把 12~36 个方位的边界点按方位角串成环，得到的就是**不规则**多边形——红绿灯、过街天桥、河流、高速、施工围挡都会让某些方向明显缩进。这不是圆，也无法用「直线距离 ÷ 速度」得到。

**精度取舍**：本方法明确是**近似**——扇形采样无法捕捉路网细粒度凹凸（如内部小巷）。用二分容差 ±30 s、网格 250 m 两个参数表达不确定性。

### 6.2 顶点采样方式五档分开（不合并）

每个边界顶点带 `sample` 标签，**刻意不合并成「已测/未测」两档**：

| 标签 | 含义 | 处置 |
| --- | --- | --- |
| `measured` | 批量算路直接测得 | — |
| `interpolated` | 二分轮次用尽后内插 | 置信度较低 |
| `extrapolated` | `R_max` 处仍未达时限，边界外推 | 置信度较低 |
| `blocked_official` | **官方禁行硬证据**（见下） | **这条路走不通** |
| `blocked_timeout` | 返回空或超时 | **我没测准，可重试** |

后两者分开的理由：它们的**可修复性与对用户的话术完全不同**。`blocked` 的官方硬判据优于「耗时超标」推断（风险 R3）：

- `direction` 返回 `links[].attr = 0x01`（禁行）
- 骑行 `restrictions_status = 0x01`（禁行）/ `0x02`（逆行）
- `status = 2001`（无骑行路线）；directionlite `status = 7`（无返回结果）

### 6.3 调用量：两个数字必须分开报告

| 口径 | 含义 | 单次体检（步行） |
| --- | --- | --- |
| `http_requests` | 真实 HTTP 往返次数 | 约 5 ~ 8 |
| `quota_units` | **配额消耗**，按 `origins × destinations` 的**路线条数**计 | 约 72 ~ 96 |
| `place_calls` | 地点检索出网次数 | ≤ 8 |

> 🔴 **批量算路按路线条数计配额，不按 HTTP 请求数计**（笔记 §1.1 Q1-25 官方原文：「批量算路的配额和并发是按最终路线数来计算，而非 RouteMatrix API 请求数」）。只报「请求数」会把配额消耗**低估一个数量级**。

### 6.4 坐标参数的三个坑（本项目最容易写错的地方）

百度官方自身的坐标参数名与顺序**并不统一**，且写错**不报错**、只会让点位静默偏移（风险 R8）：

| 接口 | 参数名 | 类型 | 坐标顺序 |
| --- | --- | --- | --- |
| 逆地理编码 | **`coordtype`**（无下划线） | **字符串** `bd09ll` | 请求 `location` 为 `纬度,经度` |
| 地点检索 | **`coord_type`** | **数字** `3` | `{lng,lat}` |
| 路线规划 / 批量算路 | **`coord_type`** | **字符串** `bd09ll` | `纬度,经度`（小数截 6 位） |

`tests/test_coord_param_table.py`（12 例）把「接口 × 参数名 × 顺序」做成常量表断言，CI 里跑。全链路统一 BD09LL，`ret_coordtype` 显式设置。

### 6.5 限流、重试与双熔断

> 🔴 **百度 Web 服务不用 HTTP 状态码表达限流。** 配额与并发限制一律以 **HTTP 200 + 响应体 `status`** 返回，**官方状态码表中不存在 HTTP 429**。按「5xx 才重试」写客户端会完全漏掉限流信号。

| `status` | 含义 | 动作 |
| --- | --- | --- |
| `1` / `8` | 服务端 / 数据异常 | 指数退避重试，最多 3 次 |
| `401` | **并发超限** | 指数退避重试，**首次退避 ≥ 1 s** |
| `4` / `302` | **当日配额耗尽，当天不可恢复** | 🔴 **立即熔断，当日不再重试**（FAQ 2361 / 2366：次日零时归零） |
| `203` / `210` / `211` / `240` 等 | 参数 / 鉴权 / AK 类型错 / 服务未开通 | **不重试**，直接降级并给可读提示 |

**双熔断器**（单一 30 s 熔断器对「配额耗尽」是错的——30 s 后重连只会加速烧配额）：

- `concurrency_breaker`：连续 5 次失败 → 打开 30 s（针对 `401`、`1`、网络超时）
- `quota_breaker`：命中 `status=4` 或 `302` → **打开至次日零时**，前端显示「该服务今日配额已用完」并自动转 `sample`

**降级链**：`内存 LRU → SQLite 缓存 → 实时调用（分桶限流）→ 合成示例数据`。任一环节失败继续下一环，响应携带 `data_source` 与 `degraded_reason`。

## 7. 评分模型

> ⚠️ **这是产品假设，不是国家标准。** 权重与阈值外置在 [`config/weights.yaml`](config/weights.yaml)；README 明确声明这一点，是为了避免被质疑权威性。若你有「15 分钟便民生活圈」地方标准文件，可替换为官方指标——但**口径要一并重写**（地方标准的指标口径可能与本项目的「官方分类计数」口径不一致）。

### 7.1 六个计分维度与达标阈值

| 维度 | 官方分类路径 | 单次 `$` 合并 query | 权重 | 达标阈值（圈内数量 / 最近实测时间） |
| --- | --- | --- | ---: | --- |
| 基础医疗 | `医疗 > 药店`、`医疗 > 综合医院`、`医疗 > 诊所` | `药店$综合医院$诊所` | 20 % | ≥ 2 个 / ≤ 8 min |
| 教育 | `教育培训 > 小学`、`教育培训 > 幼儿园` | `小学$幼儿园` | 15 % | ≥ 1 个 / ≤ 12 min |
| 购物市场 | `购物 > 市场`、`购物 > 超市`、`购物 > 便利店` | `市场$超市$便利店` | 20 % | ≥ 3 个 / ≤ 8 min |
| 养老休闲 | `旅游景点 > 公园`、`休闲娱乐 > 休闲广场`、`运动健身 > 健身中心`、`医疗 > 疗养院` | `公园$休闲广场$健身中心$疗养院` | 15 % | ≥ 1 个 / ≤ 10 min |
| 公共交通 | `交通设施 > 公交车站`、`交通设施 > 地铁站` | `公交车站$地铁站` | 15 % | **公交车站** ≥ 2 个 / ≤ 5 min |
| 餐饮服务 | `美食 > 中餐厅`、`美食 > 小吃快餐店` | `中餐厅$小吃快餐店` | 10 % | ≥ 5 个 / ≤ 10 min |
| 便民服务（参考项） | `金融 > 银行`、`金融 > ATM`、`生活服务 > 维修点` | `银行$ATM$维修点` | 0 % | 不计分，仅列入明细表 |

- **一个维度只用一次请求**：圆形区域检索的 `query` 支持多关键字并集、`$` 分隔、最多 10 个。这是把 v1.0 的「6 类 × 2~4 别名 = 12~24 次」压进个人档 **100 次/日** 的关键手段。
- **公共交通的阈值只管「公交车站」**：PRD 原文写的是「公交车站 ≥ 2 个」而不是「本维度 ≥ 2 个」。只看维度计数会让「2 个地铁站、0 个公交站」被误判为达标。
- **类别判定走结构化字段**：用返回体的 `tag` / `classified_poi_tag` 判定，不依赖自由文本 `query` 是否命中；同一 POI 被多个别名命中时按百度 `uid` 去重（FR-214）。

### 7.2 单维度得分与总分

```
单维度得分 S_i = 100 × (0.5 × 数量分 + 0.5 × 时效分)
  数量分 = min(圈内该类数量 / 达标阈值数量, 1)
  时效分 = clamp((T_上限 − 最近实测时间) / (T_上限 − T_理想), 0, 1)
           T_理想 = 阈值时间 × 0.5，T_上限 = 15 min
总分   = Σ (S_i × w_i)
盲区惩罚 = 每 1 % 圈内面积被标记为完全盲区，总分 −0.5，上限 −15
```

**等级线**：`A ≥ 85` · `B 70 ~ 84` · `C 55 ~ 69` · `D < 55`

评分函数是**纯函数**——给定同一份 `coverage` + `blind_spots`，输出恒定（FR-301「分数可复算」），`tests/test_score.py` 用「打乱输入顺序 + 重复调用」两条断言钉住。

### 7.3 🔴 六维权重合计 95 % 而非 100 %：本项目的显式裁决

PRD §4.3 的权重表是 **20+15+20+15+15+10 = 95 %**，而 §4.5 的等级线 `A ≥ 85 / B 70~84 / C 55~69 / D < 55` 写在 **0~100 刻度**上。两种读法都自洽：

- **不归一**（照 §4.5 字面 `总分 = Σ(S_i × w_i)`）：满分只有 95，A 档实际要求「达到可达上限的 89.5 %」——而这个 89.5 % 在任何文档里都没写过。
- **归一**（除以计分权重之和 0.95）：满分 100，A 档就是字面的「85 分」。

本项目的裁决是**默认归一**（A 线自洽，且「权重」一词的常规读法就是相对权重）。为了让裁决可被审计、也可被推翻，响应里**同时**给出：

| 字段 | 含义 |
| --- | --- |
| `score.total` | 用于评级的那个（默认归一） |
| `score.total_raw` | §4.5 字面值 |
| `score.weight_sum` | 计分权重之和（`0.95`） |
| `score.grade_basis` | `normalized` 或字面口径 |

要改回字面口径：把 [`config/weights.yaml`](config/weights.yaml) 里的 `normalize_weights` 改成 `false`（`services/score.py:load_score_config()` 读该键，默认 `true`）。

> ⚠️ **这个开关只能走 YAML，没有对应的环境变量。** `services/score.py` 的模块 docstring 里提到过「`.env` 里给 `SCORE_NORMALIZE_WEIGHTS=false`」，但 `infra/config.py` 与 `.env.example` 里**都没有这个键**——照 docstring 去 `.env` 里找会白费功夫。以本节为准。

**实测复算**（`data_mode=mock`、步行 15 min，`total = total_raw / 0.95 − min(盲区% × 0.5, 15)`）：

| 样例 | `total_raw` | 盲区面积 | `total` | 等级 | 复算 |
| --- | ---: | ---: | ---: | --- | --- |
| 交道口街道 | 95.00 | 7.5905 % | **96.20** | A | 100 − 3.795 = 96.20 ✓ |
| 天通苑 | 89.18 | 18.4396 % | **84.66** | B | 93.87 − 9.220 = 84.65 ✓ |
| 肖家河 | 56.45 | 96.8115 % | **44.42** | D | 59.42 − 15（封顶）= 44.42 ✓ |

### 7.4 盲区判定（两级阈值）

| 级别 | 判定 | 渲染 |
| --- | --- | --- |
| 完全盲区（FR-221 主判定） | 网格点 1 km 半径内 **市场 ∩ 药店 ∩ 小学 三类皆无** | 灰色 |
| 配套不足（FR-224 次判定） | 只缺 1~2 类 | 橙色 |

> **需求澄清**：命题原文「周边 1 公里内没有菜市场、药店或小学」存在两种读法——(a) 三者**皆无**（严格盲区）；(b) **任一**缺失即算不足。本项目**两种口径同时呈现**，避免评审按另一种理解判定时失分。

判定粒度是 **`subcat` 而非维度**：药店属于 `medical` 维度，而该维度还含综合医院/诊所——**整维度非空不等于有药店**。

盲区判定 **0 次 API 调用**，完全复用已拉取的 POI 集合做本地球面距离（haversine）计算（决策 D5）。这是把盲区识别从 O(N×3) 次调用降到 0 次的核心优化。

### 7.5 命题「菜市场」→ 官方「市场」的映射（README 必须讲清）

🔴 命题原文写「菜市场」，但**百度官方 POI 分类表中不存在这个分类**，对应项是 **`购物 > 市场`**。本项目按「市场」（`subcat="market"`）判定，并把这个映射做成机器断言（`services/poi_categories.py:PRD_V1_TERM_REPLACEMENTS`，CI 里跑）——因为「保留不存在的词」最坏的后果不是检索为空，而是**该维度永远计数 0、被误判成「这个社区缺配套」**，直接污染盲区结论。

| 命题原文 / PRD v1.0 用词 | 处置 |
| --- | --- |
| 菜市场 | → 市场 |
| 农贸市场 | → 市场 |
| 养老院 | → 疗养院 |
| 社区卫生服务中心 | → 诊所 |
| 银行网点 | → 银行 |
| 社区服务中心 | **删除**（官方分类表中不存在） |
| 快递驿站 | **删除**（同上） |
| 理发店 | **删除**（同上） |

### 8.1 预案 A —— 可出网，走 `live` 全链路

**前提**：本机可访问 `api.map.baidu.com`，且已配置有效的服务端 + 浏览器端 AK，且当日配额未耗尽。

## 9. 数据来源与合规声明（FR-413）

本项目遵循《百度地图开放平台产品和服务协议》（官方页自注更新于 2026-08-05）。逐条判定见 [`docs/BAIDU_API_NOTES.md`](docs/BAIDU_API_NOTES.md) §7。

### 9.1 数据来源披露

本服务**使用百度地图开放平台**（Web 服务 API：地理编码 / 逆地理编码 / 地点检索 / 批量算路；浏览器端 JSAPI 4.0）。依据条款 **7.3**，须向用户显著披露使用本服务并提供《百度地图开放平台隐私政策》链接。

### 9.2 缓存：仅是减少重复调用的技术措施

**依据条款 3.3.2(ii)**：官方明文把「存储、缓存」列为对被释放数据的禁止操作之一。因此本项目的缓存被严格定位为 **「同进程运行时性能缓存」，不是数据资产库**：

| 约束 | 落实方式 |
| --- | --- |
| 表结构收敛 | `cache(key, service, payload, created_at, expires_at)`——**不建** `pois(id, name, category, lng, lat)` 这类可查询的 POI 维度表（后者字面命中条款 3.3.4「生成或用于数据库」） |
| POI TTL ≤ 24 h | `CACHE_TTL_PLACE_S=86400`，填更大会被强制夹回 |
| 过期行物理删除 | 启动时与每次写入时清理 |
| 镜像不得预置 `.db` | `.dockerignore` 排除 `**/*.db` 及 `.db-wal`/`.db-shm`/`.db-journal`；`Dockerfile` 逐个目录 `COPY` 而非 `COPY . .`；CI 有一条 `find /app -name "*.db"` 断言 |
| 不得成为对外数据源 | 任何 API 响应都不得把缓存中的百度原始记录输出为可批量导出的数据集 |

> ⚠️ **官方从未公开「允许缓存多久」这个数值。** TTL 的具体取值（地理编码 30 天 / POI 24 h / 路线 7 天）是**本产品的假设**，依据是「TTL 越短越接近性能缓存」这一判断，不是官方规定。

### 9.3 示例数据一律程序合成

**依据条款 3.3.4 与 6.3**：把百度返回「生成或用于数据库」、以及把运营数据用于其他目的，均属禁止形态。因此：

- v1.0 原设计的「真实调一次、把返回存成 JSON 随镜像分发」**已被推翻**，改为由我方算法**按给定中心点合成**等时圈顶点与设施点（`tools/gen_samples.py`）。

### 10.4 🔴 报告图表用手绘 SVG，而非 PRD §5 写的 ECharts

**这是本项目对 PRD 的一处显式偏离，必须读。**

1. Vue global build + ECharts（**仅引雷达/柱状模块**）本地 vendored

| ECharts `full` | 1 007 KB | — |

### 10.5 🔴 前 K 实测用了分层选择，而非 §4.3 字面的全局最近 K

**这是第二处对 PRD 的显式偏离，附实测数字。**

PRD §4.3 第 4 条写的是「圈内 + **直线距离最近的前 K 个**」，K 是全局的。**按字面实现后，实测三样例出现倒挂**：

| 样例 | 建成形态 | 圈内点位数 | 总分（字面口径） | 等级 | 盲区面积 |
| --- | --- | ---: | ---: | --- | ---: |
| 交道口街道 | 成熟老城 | 48 | **67.25** | **C** | 7.59 % |
| 天通苑 | 新建大盘 | 14 | **84.66** | **B** | 18.44 % |
| 肖家河 | 城中村 | 23 | 44.42 | D | 96.81 % |

**机制**：密集社区的圈内点位多，全局最近的 12 个名额可能全被餐饮与便利店占满，于是医疗 / 购物 / 公交三个维度**一个都没实测到** → `nearest_minutes = None` → §4.5 的时效分记 0（`services/coverage.py` 刻意拒绝用直线距离顶替实测时间）→ 这三个维度被硬压在 50 分。而稀疏社区点位少、几乎人人有实测值，六个维度时效分反而满分。

**净效果是「设施越全、得分越低」——与事实相反，会直接误导评审。**

而 §4.3 的达标阈值表本身写的是「圈内数量 / **最近实测时间**」，逐维度都要一个实测时间，这说明 **PRD 的本意就是每个维度都得测到**，只是没写清 K 该怎么分配。

**修复**：新增分层选择 `select_measurement_targets_fair()`——先给每个维度留一个最近点，再用全局最近点填满剩余名额。**K 总量、批次数量、配额消耗完全不变**，改变的只是名额分配。修复后：

| 样例 | 总分 | 等级 | 六维雷达最小值 |
| --- | ---: | --- | ---: |
| 交道口街道 | **96.20** | A | 100 |
| 天通苑 | 84.66 | B | 74.09 |
| 肖家河 | 44.42 | D | 0 |

排序符合建成形态的事实。**要回到字面口径**：调用 `build_coverage(..., selection="nearest")`；报告里 `coverage.meta.selection` 会如实回显本次用了哪一种（默认 `fair`），`selection_definition` 一并给出两种口径的定义。理由、证据与回退方式写在 `services/coverage.py:SELECTION_FAIR` 的长注释里。

> 附带说明：肖家河的医疗与教育为 **0 分是真实结论而非缺数据**——`transit_corridor` 画像里药店与小学的合成条数就是 0，`count_in = 0` → `nearest_reason = no_poi_in_polygon` → 时效分按 0 计。它演示的正是「能上车、买不到菜」那类地方。

### 10.6 🔴 无 `live` 模式实测记录

**本项目从未有过可用的百度 AK。**

这不是遗漏，是既定条件。后果：

| 影响面 | 说明 |
| --- | --- |
| 实时链路 | 所有「实时链路」的验证都在 `httpx.MockTransport` 上完成（不建任何连接） |
| 演示预案 A | **必须在有 AK 的机器上另行实跑一次**（§8.1） |
| §2.2 的耗时指标 | 「冷启动 ≤ 25 s / 缓存命中 ≤ 3 s」是 PRD 的**目标值**，**从未实测** |
| 「实测 vs 插值」偏差 | [`docs/TEST_REPORT.md`](docs/TEST_REPORT.md) §5 明确回答：**无法给出**，因为没有真实测时样本 |
| 样例坐标核验 | 见 §10.1，`coord_verified: false` |

**已知的、与真实网络无关的可精确测量**（这些是实测值，不是推算）：HTTP 请求数、配额单位、本地 CPU 耗时、限流排队时长、合成路径的全部报告数字。依赖真实网络才能得到的（线上墙钟耗时）一律标注为**推算**并给出假设参数。

### 10.7 其他未验证项

| 项 | 说明 |
| --- | --- |
| **浏览器内真实渲染** | 本环境的无头 Chrome 无输出（被沙箱挡住）。改用 Node + 最小 DOM 打桩**真跑** `web/report.js` 的渲染路径（`tools/report_dom_smoke.mjs`，12 项断言全部通过），但它**不是**真实浏览器 |
| **前端截图** | 本项目历史上浏览器**无法落地截图**（browser-use 报 `NATIVE_BROWSER_VIEWPORT_UNAVAILABLE`，`visibilityState=hidden`、无可见 surface）。所以本文**不提供效果截图**——`docs/shots/` 下以 DOM 计数、计算样式、network / console 文字证据替代 PNG |
| **JSAPI 实时底图上的顶点点击** | 只跑到 SVG 降级引擎；`BMap.Marker` 点击那条路径未验（因为禁真实出网） |
| **DevTools Network offline 下的全链路降级** | 本环境无网络拦截工具且禁真实出网，只跑了代码审读与真实失败出口调用 |
| **`docs/DESIGN.md`** | 技术设计文档（PRD FR-411 指定落点）已补齐。本文只做「怎么用」与「已知局限」，算法推导、调用策略、合规判定与三处对 PRD 的显式偏离**正文在 `docs/DESIGN.md`**，两处不重复抄写以免失同步 |
| **官方未公开 / 需实测的盲区** | `localhost` 能否作为 Referer 白名单（§3.3）；地点检索 `page_size` 真实上限是 10 还是 20（官方三处自相矛盾，本项目按保守值 10 设计且一律不翻页）；逆地理 `pois` 返回条数上限；JSAPI 4.0 下 `BMapLib` 热力图插件能否工作（本项目走自绘，不依赖此项） |
